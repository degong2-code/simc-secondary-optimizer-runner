# P1 · 업데이트 가능한 데이터/계산 구조 — 공통 구현 원칙

사용자 의도: **이번 시즌의 값 몇 개를 코드에 붙이는 방식이 아니라, 새로운 시즌·SimC 버전·장신구/아이템 데이터가 들어와도 같은 검증된 실행 경로를 재사용**한다. '엔진'은 모든 구성 요소를 새 프레임워크로 만드는 뜻이 아니다. 책임과 입력 계약을 공통화하여 구조적 재작성 없이 **데이터 교체 + 영향 범위별 최소 시험**으로 유지하는 것이 목표.

## 핵심 책임 분리

| 구간 | 책임 | 구현/범위 |
|---|---|---|
| 1. 원본 수집 및 출처 | 신뢰 가능한 시즌/아이템/SimC Native 원본·버전·정확 ID/ilvl/options 확보. **미관측은 0이 아님.** | 기존 v144 catalog provenance, Native/정적 receipt. *공식 자동 동기화는 미구현* |
| 2. 입력 정규화 및 버전 | 프로필·장비·티어·특성 계약과 시즌별 아이템 ID/기름/소모품 분리 | v143 고정 spec 계약 + v144 시즌 데이터 + v139 재사용 profile composer |
| 3. 변경 영향 계산 | 과거/새 시즌 catalog를 비교해 동일·메타 변경·개별 전문화·공통 장비/보석·소모품·레벨 변경을 구분 | **v151**. 원본 파일 읽기만 수행, Native 0회, 미분류 데이터 필드는 명시 리뷰 |
| 4. 실행 및 결과 | 표준 대표 장비 → B/T/L/O/중복 방지 → 같은 적응형 SimC DPS/SEM/95% | v098→v096→v094. SimC가 기전·APL·장비 효과 소유 |
| 5. 캐시와 승인 범위 | 바뀌지 않은 정적 아이템 데이터 보존; DPS는 exact 바이너리 SHA/revision·프로필·조건·후보·iterations identity로 구분. 과거 영수증 불변 | v106/v094/Native receipt. **새 시즌 데이터가 새 세션 identity로 구분되는 정식 snapshot 라우팅은 추후 구현** |
| 6. 검증/운영 | UI 수정=0 Native, 전문화 장비 차이=변경 spec, 공통 아이템=영향 전체 물리 검토, 소모품/밸런스=DPS 영향 spec, 신규 시즌=검증된 데이터와 필요한 Native만 | v151 영향 계획 + 기존 offline CI + 필요 시 Windows Native. 자동 전수 24×6 금지 |

## v151 예시 — 데이터 두 벌만 입력

```powershell
py -3 runner/v151_season_catalog_impact.py --before "C:\path\old_season.json" --after "C:\path\new_season.json"
```

출력: `before_sha256`/`after_sha256`, 변경된 공통/전문화별 항목, `needs_physical_acceptance_review`, `needs_adaptive_dps_review`, `budget_policy_review_required`, 미분류 항목 및 신규 Native 호출 `0`. 이 목록은 **검토 범위**, 즉 *일괄 실행 요청*이나 *자동 정상 판정*이 아니다. 메타데이터/출처 설명만 바뀌면 0 Native 대상으로 표기한다.

현재 시즌 기준은 `integration_probes/catalog/v144_mid2_season_items.json`, 실제 승인 target은 **334**다. 기존 v139 compiler는 입력 catalog에 목표 레벨과 그에 맞는 장비 ID를 넣으면 프로필을 구성할 수 있으나, **새 목표 레벨용 catalog 근거 + 시즌 참조 예산 + 실제 Native 수용이 없으면 제품 사용자 지원을 해제하지 않는다**. v151의 비교 결과만으로 새 레벨/시즌을 승인하지 않는다.

## 새로운 데이터 소스가 생겼을 때 적용할 규칙

- 스크래핑/수집·공식 API·Native 소스는 **별도 어댑터**, 검증된 정규화 포맷이 본체. 같은 출처를 반복 수집하거나 전체 SimC 프로필을 전수 다운로드하지 않는다.
- 키(ID+ilvl+options), 패치/시즌, 확인된 source/receipt/hash 및 출처 범위는 보존한다. 관측에 없는 숫자는 추정/0으로 채우지 않는다.
- 바뀐 데이터만 갱신하고 캐시·실측 Native 영수증은 기존 시즌과 분리해 보관한다. 정적 데이터는 SimC revision 변경만으로 일괄 폐기하지 않는다.
- *새 데이터 자체가 무엇인지*, *어떤 코드가 자동으로 쓰는지*, *어떤 범위가 Native로 확인됐는지*를 각 상태 보고에 구분한다.
- 유지비 절약 목적에 직접 기여하지 않는 새 엔진·Gate·API 호출·복잡한 파일 포맷은 만들지 않는다. v151은 이미 있는 v139 검증자를 재사용해 새 데이터 validation 루프를 중복하지 않는다.
- 캐시 identity에 새 catalog snapshot을 반영하는 후속 변경은 기존 **사용자 Windows 6/6 Native 완료** 세션 ID와 불변 영수증을 훼손하지 않도록 구버전 이식·분리 정책부터 설계한다. 동일 사용자 새 시즌 실행을 옛 캐시에 조용히 붙이면 안 된다.

## 현재 완료 범위와 향후 과제

**구현됨:** 정적 class 계약과 교체 가능한 시즌 대표 카탈로그/컴파일러, v151 순수 catalog 변경 분석, 구조적 대상 선별, v098/v096/v094 적응형 실행, 기존 사용자 세션/영수증/95% 결과, 오프라인 CI. 

**아직 미구현:** 새 시즌 공식 데이터를 자동 수집·검증·가져오기, 실제 334 외 레벨의 검증된 카탈로그/동일 v139 사용자 실행 경로, SimC/게임 변경 자동 감시, 완전한 catalog snapshot identity 충돌 방지/이식, 탱커/힐러 전문화 데이터 보급. 외부 출처로부터 근거 없는 변경을 자동 승인하지 않는다.

이 원칙은 **시즌 자료에만 한정된 것이 아니라** 향후 새 입력/장신구·장식·보석·기름·특성/SimC 기전/결과 UI에도 적용한다. 단, 실행 엔진이나 검증 Gate를 분야마다 따로 복제하지 않는다.
