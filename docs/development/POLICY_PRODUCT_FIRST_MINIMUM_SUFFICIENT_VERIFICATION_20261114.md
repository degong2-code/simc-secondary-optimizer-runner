# SIMC SECONDARY OPTIMIZER — 제품 우선·최소 충분 검증 상시 운영 정책

> **사용자 직접 결정 · 2026-11-14. 모든 제품 개발 채팅·독립 인계 채팅에 적용.**
> 기존 승인 제품 설계(v1.4.3 및 비충돌 정책)의 **개발 우선순위·검증 범위 해석**을 명료화한다. 원래의 아이템/예산 책임, 정확성, 78개 상태 원장 및 정식 COMPLETE 판정은 완화·위조하지 않는다. GitHub 기록 자체가 Project UI 설정 변경은 아니다.

## 1. 평가 대상은 검증 항목 수가 아닌 작동하는 사용자 제품

- 목표: **26개 DPS 전문화**에서 목표 ilvl(기본 334) 또는 사용자 최종 T에 맞는 **치명·가속·특화·유연 절대 rating**을 기존 적응형 SimC DPS로 최적화하고, DPS·SEM·명목 95% 판정·관측 1순위·실질적으로 다른 근접 대안·비율을 제공한다.
- 주 사용자 경로: **사용자 선택 → 현재 시즌 G/J/F/O 및 B/T 검증 → 내부 대표 일반 장비·무기·티어 4pc·SimC 프로필 구성 → 기존 SimC 적응형 실행/캐시/취소·재개 → 결과**. 지금 이 경로를 막는 결함·누락을 최우선으로 수정한다.
- 현재 장비의 스탯 재분배, 장비 조합/획득 추천, 전체 시즌 장비 DB, 독립 효과/발동/APL 엔진, 전 품목 인증, 무조건적 Native 전수·새 알고리즘 연구는 제품 범위 밖이다.

## 2. 검증의 한계: 실제 제품이 소비하는 최소 충분 증거

- 실제 사용하는 **원본 ItemID/ilvl/슬롯/옵션/게임빌드·시즌, 대표 G/J/F/O, 수동 T, L/E/O 1회 계상·고정 하한, SimC 입력·JSON2 정합, 정확한 캐시·결과**는 필요 범위에서 확실히 검증한다. 미관측을 0 또는 전 시즌 값으로 대체하지 않는다.
- **SimC가 장비/보석/소모품/기름 효과, proc, APL, 실제 DPS를 계산**한다. 소모품 사용 주문 → 내부 SpellEffect → 추가 주문 연쇄를 프로그램이 완벽하게 역추적하거나 독립 인증하는 일을 정상 조건으로 만들지 않는다. SimC 실제 오류는 원문과 입력·실제 관측 범위를 보고한다.
- 먼저 기존 v216/v217/v212, v098/v096/v094, 같은 시즌 봉인 원본·SHA·캐시·Native/Actions를 **재사용**한다. 실제로 부족한 소비 필드에 한해 읽거나 연결한다. 요청과 무관한 DB2/스펠/장비를 새로 수집하거나 보관하지 않는다.
- 선택형 보석 추가/특수 효과/촉매/시즌 모듈 등은 **사용자가 실제 선택하고 현재 실행에 필요한 경우에만** 해당 입력·예산의 적용 조건을 검증한다. 정확한 증거가 없으면 **그 선택지만 PENDING/비노출/명확한 실패**로 보존하고, 다른 검증된 BASE 환경과 일반 사용자 SimC 실행을 막지 않는다.
- 새 시즌 기본 **G/J/F/O 전체 자동 구축과 B/T** 및 선택 고정치·사용자 프로필의 핵심 정합은 여전히 필수. 기본 환경 필수 증거까지 생략해 READY를 주장하지 않는다. 선택된 필수 입력이 미확정이면 그 시나리오는 fail-closed 한다.

## 3. 78요소 원장과 개발 실행 순서는 다르다

- 78개 ID/네 축 `generic/current_source/product_integration/historical`, `COMPLETE` 판정, 원본 SHA·실증·엄격 전체 USER-E2E 요건은 **그대로 유지**한다. 없는 근거로 PASS/N/A/READY를 만들지 않는다.
- `policy.next_review=B10` 등은 **원장의 다음 판정·감사 위치**이다. **지금 당장 B10 전체를 해결해야만 P1의 다른 일반 제품 기능을 구현·시험할 수 있다는 명령이 아니다.** `next_review`를 임의로 덮어쓰지도 않는다.
- 작업 선택은 현재 사용자 제품의 **첫 실제 장애물**로 결정한다. 78개를 번호 순으로 검사하기 위해 더 많은 독립 Gate/수집/Native를 만들어서는 안 된다. 그 사이 다른 일반 제품 기능 개발·시험을 계속할 수 있다.
- 최종 전체 제품 COMPLETE/정식 READY를 주장할 때는 기존 v401의 유효한 해당 범위 수락·최종 ZERO-SOURCE→USER-E2E 요건을 충족한다. **개발 가능**과 **최종 승인**을 구분한다.

## 4. 기능 추가·자료 수집 전 반드시 적용할 6문항

1. **사용자 가치:** 이 작업이 실제 사용자 선택→최적 rating·DPS 결과 경로의 어떤 결함/차단을 해결하는가? 수정 후 누가 어떤 기능을 쓸 수 있는가?
2. **소비 범위:** 제품이 직접 사용하는 구체적인 필드·예산·옵션은 무엇인가? 이름이 비슷하거나 SimC 내부 전용인 자료는 제외했는가?
3. **기존 자산:** 기존 코드·정적 캐시·같은 시즌 봉인 영수증·Native 증거로 `REUSE/CONNECT/FIX`가 가능한가?
4. **비선택 기능 격리:** 해당 옵션이 미선택·미검증이어도 BASE를 계속 실행할 수 있는가? 사용자 선택을 정확히 막는 것으로 충분한가?
5. **비용:** 새 네트워크/DB2/Native/파일·메모리·CPU·I/O·미래 시즌 유지비는 얼마이며 더 작은 검증 수단은 없는가?
6. **중단 기준:** 기존 보존 증거로 사용자 기능을 정확하게 처리할 수 있으면 **STOP**. 추가 조사가 사용자 제품 판정을 바꾸지 않으면 **STOP**. 단지 `PASS` 항목을 늘리기 위한 코딩이면 **STOP**.

실행 선택은 `STOP → REUSE → CONNECT/FIX → 필요한 최소 EXTEND → 최후 NEW` 순으로 검토한다. 신규 효과 해석기/영구 소스 서브시스템/대량 전수 테스트는 사용자 명시적 신규 범위 승인이나 **검증된 기존 사용자 기능을 해결할 다른 방법이 없는 명확한 제품 결함**이 없는 한 시작하지 않는다.

## 5. 현재 B10 교정 사례와 다음 행동

- v445~v451의 **대표 기본 소켓·보석 ID/ItemID·J 소유권 일관성/실패 차단**은 실제 입력 안정성에 기여하므로 보존한다.
- v452~v455의 **70783 v280 ItemID→사용 주문·v281 SpellEffect 실측 영수증**은 이미 취득한 연구 증거로 보존한다. 그러나 사용 주문 1309820/1297709 등의 내부 효과 연쇄·시즌별 모든 추가 소켓 메커니즘을 **계속 추적하는 작업은 중단**한다.
- v455의 5+ 선택형 원본 진단 코드가 **실제 사용자 기능에 필요한지 추후 좁게 검토**하되, 아직 제거하거나 PASS를 새로 선언한 것은 아니다. 삭제/개편도 실제 결함·비용·회귀를 먼저 확인한다.
- 기본 4보석·검증된 G/J/F/O → 대표 프로필 → 기존 적응형 SimC → 실제 결과/취소·재개에서 **현재 막힌 첫 경계**를 다음 개발 후보로 고른다. 추가 소켓 옵션 미검증은 해당 옵션만 보류한다.

## 6. 새 채팅 인계·보고 방식

- 모든 후속 개발/인계 채팅은 시작 시 **이 문서를 먼저 읽고**, 최신 사용자 지시·현 실제 HEAD·CURRENT·상태 JSON·Actions/Native 영수증을 대조한다. 역사 인계의 `next B10`, 오래된 PASS 수치를 자동 개발 지시로 오해하지 않는다.
- 시작 보고: **(a) 제품 최종 목적 (b) 지금 일반 사용자가 할 수 있는 것/막힌 것 (c) 필수 vs 선택적 미확정 (d) 비용이 가장 낮은 단일 다음 작업 (e) 추가 검증이 불필요한 항목과 STOP 사유**.

- 새 인계 채팅이 명시적으로 **읽기 전용 복원** 요청을 받았다면 정보 복원 후 STOP; 별도 `진행` 이전에는 코드·GitHub 문서·Actions를 수정하지 않는다. 주 제품 개발 채팅의 구현 소유권, 격리 브랜치, main/v003/v016/Project UI·Work OS 공식 승격 권한은 변경하지 않는다.

**이 문서를 변경할 수 있는 기준은 최신 사용자 직접 결정뿐이다. 정책 내용을 반복해서 새로운 문서·수집 Gate·코드로 복제하지 말고 기존 시작점에서 본문 링크로 재사용한다.**
