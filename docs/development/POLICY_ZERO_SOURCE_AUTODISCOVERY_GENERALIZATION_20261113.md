# 2026-11-13 최신 사용자 결정 — 현재 시즌 ZERO-SOURCE 성공으로 미래 시즌 대응 **엔진 기능** 검증 완료

> **상시 필수 기준.** 최신 사용자 직접 결정이며 [운영 헌장](OPERATING_CHARTER_FUTURE_SEASONS_AND_EVIDENCE_20261113.md), [78개 원장](ENVIRONMENT_READINESS_78_ELEMENT_TRACKER_20261113.md), [인계](../CHAT_CONTINUITY_HANDOFF_20261113_P1_V382_78_ELEMENT_READINESS.md)에 우선 적용한다. 이것은 설계·수락 정책이지 이미 달성한 신규 PASS/시즌 READY 영수증이 아니다.

## 1. 정확한 완료 판정

- **미래의 데이터 실존을 기다리지 않는다.** 아직 오지 않은 확장팩의 미공개 ID, 티어, 아이템, G/J/F/O를 현재 미리 실측/인증할 수 없다는 이유만으로, 해당 **범용 발견·수집·검증 엔진 기능**을 `PENDING_SCOPE`로 고정하지 않는다.
- 현재 시점에 **완전한 ZERO-SOURCE**로 실행한다. 시즌/확장팩 이름·ID, 활성 레이드·시즌 아이템, 정답 DB/완성 catalog/manifest, 예산 G/J/F/O, 기존 성공 캐시·프로필을 사전 주입하지 않는다. 개발자·GPT·사용자의 런타임 선택/판정/웹검색 개입 없이 **기존 제품 호출 경로의 코드만**으로 작업한다.
- **출처 접근은 정상적으로 허용한다.** 엔진에 이미 연결된 승인 원본(Blizzard API, 승인 외부 WCL API, 동시즌 DB2, pinned SimC 등)의 실제 응답·필드/관계/SHA를 사용하며, 필요한 OAuth/API 키와 네트워크 권한이 갖춰진 환경이 시험의 기본 전제다. 자격 증명이 없는 별도 네거티브 시험의 PENDING은 이 정상 조건의 구현 FAIL과 구분한다. 테스트 편의를 위해 시즌 정답을 API 키로 대신 주입하지 않는다.
- **식별 기준은 구조·관계·시간에 근거한다.** 예: 출처의 `current/active` 식별자, 빌드/시즌 유효범위, 콘텐츠 관계, 날짜·배포/유효 시작·종료·버전, DB2/SimC 정확 동일 빌드/품질/ID 관계. 단순 이름 `Midnight`, 역사 ID, 특정 현재 레이드명/품목/확장팩 번호, 최신 수정일 1개만으로 확정 금지. 출처의 실제 의미를 읽고 충돌/동률/미해석은 관련 선택만 정확히 보류한다. 하나의 필드를 쓰든 여러 필드로 조인하든 **합리적 근거와 원본 재현성**이 있어야 한다.
- **실제 관측 성공이 필수다.** 현재 시즌·확장팩을 코드가 **자동으로 정확히 찾아내고**, 해당 기능이 제품에서 소비하는 범위의 원본을 자동 획득·검증해 출처·빌드·ID·SHA·관계와 올바른 결과를 독립 대조한다. 빈 루트에서 실제 이 경로의 테스트가 PASS면 **그 78개 항목의 범용 엔진 기능을 검증 완료**로 판정한다. 새 미래 시즌에 실행해 봐야만 PASS한다는 추가 선행 Gate는 두지 않는다.
- **가상 변형 회귀는 보강 수단**이다. 다른 확장팩명/시즌 ID·변경 빌드/시간·여러 후보·충돌/조건 누락/소스 교체 등을 합성 입력으로 검증하여 현재 시즌 하드코딩/우연 성공을 탐지한다. 단, 실제 ZERO-SOURCE 성공을 합성 테스트로 대체하지 않는다.

## 2. 네 가지 판정을 분리

| 판정 | 의미 | 이 정책에서 PASS를 얻는 조건 |
|---|---|---|
| `ENGINE_AUTODISCOVERY_PASS` | 시즌을 몰라도 구조적으로 찾고 올바른 필수 원본을 수집하는 코드 기능 | 현재 **정답 미주입** ZERO-SOURCE 실제 성공 + 원본 관계/시간·필드 증거 및 변형 회귀 |
| `CURRENT_SEASON_SOURCE_READY_SCOPED` | 해당 현재 시즌·사용자 선택 범위에서 정확한 item/GJFO/설치 증거 | 같은 빌드·선택 경로의 실제 인증/봉인/수치 정합 |
| `CURRENT_SEASON_ZERO_SOURCE_USER_E2E_PASS` | 최종 사용자 입력→환경→SimC→결과/취소·재개/캐시 | 78개 필요한 적용 범위 정리 후 실제 제품 종단 간 인수 시험 |
| `FUTURE_NEW_SEASON_RUN` | 새 시즌이 출시된 **이후** 실제 출처 변경/호환성/신규 자료 검증 | 출시 후 재실행; 엔진 기능의 현재 완료 판정을 미래 미출시라는 이유로 소급 보류하지 않음 |

**주의:** 현재 ZERO-SOURCE에서 A1 자동 식별 성공은 A1 **ENGINE PASS**이지, B~H 전체 READY나 미래 미공개 아이템 수치 선인증이 아니다. 단일 사례 우연 맞힘은 범용 PASS가 아니며 날짜/출처/ID가 바뀌어도 합리적으로 작동함을 다른 값의 회귀로 검사한다.

## 3. 78개 순차 개발·기록·인계의 의무

1. **A1부터 A11, B1~B12, C1~C14, D1~D9, E1~E9, F1~F7, G1~G10, H1~H6 전부 누락 없이 추적.** 의존성 때문에 실제 구현·실행을 묶거나 재정렬할 수 있지만 해당 ID를 생략하지 않는다. A1이 아직 PENDING이면 이유와 재개 조건을 남기고, 확인 없이 A2의 완료로 덮지 않는다.
2. **각 ID:** 계약/제품 소비 필드·원본 공급자·실제 코드 연결→과거 receipt SHA/Actions/Native 분리→변경 REUSE/CONNECT/EXTEND/NEW 최소화→현재 범위 실제 PASS/FAIL 및 재현 절차→남은 경계/다음 ID. 완료 카운트는 **역사 READY_SCOPED / 현재 ENGINE PASS / 현재 SEASON READY / 최종 E2E**를 구분한다.
3. **실패 시** 마지막 성공 stage·원본 SHA→첫 `status/missing`·G/J/F/O 소유자 불일치→관련 78개 ID→과거 동일 조건 영수증을 비교한다. 새 엔진 작성이나 모든 Native 재실행부터 시작하지 않는다.
4. **종단 인수 Gate:** 78개 적용 범위가 정리되어도 제품 전체 완료에는 별도의 현재 실제 시즌 `ZERO-SOURCE→USER-E2E` PASS가 필요하다. 개발 중엔 최소 국소/경계/필요 E2E를 계속 검증한다.
5. **다음 채팅도 필수 적용:** [START_HERE](START_HERE.md)→이 정책→[운영 헌장](OPERATING_CHARTER_FUTURE_SEASONS_AND_EVIDENCE_20261113.md)→[PROTOCOL](PROTOCOL.md)→[78개 원장](ENVIRONMENT_READINESS_78_ELEMENT_TRACKER_20261113.md)→[단일 인계](../CHAT_CONTINUITY_HANDOFF_20261113_P1_V382_78_ELEMENT_READINESS.md)→관련 코드/원본. 문서 작성만으로 Project UI 설정, main 병합, 공식 승격을 완료했다고 주장하지 않는다.

## 4. 첫 적용 대상 A1 (현 개발 상태)

- `v289`: 공식 Retail KR 현재 **게임 빌드** 발견은 존재; 빌드 번호 자체가 확장팩/시즌 소속 전체의 독립 증거는 아니다.
