**필수 오해 방지:** 원형 v290의 1008회는 실제 약 7만 iterations, v312의 1008회는 39,840으로 달랐던 실험이 있다. 호출 수가 같은 표를 공정한 **총 계산량 동일** 비교로 표시하지 않는다. 95%는 명목 비교와 다중선택/가족단위 보정 여부를 분리한다. 전역 최적 입증은 하지 않는다. 전문화 간 DPS 원값 평균을 내지 않는다.

**통합 표를 채울 때:** 실행 정책 ID | 시나리오 ID | 새 source SHA | binary/build | wall 5/10분 최고 정밀 DPS/SEM | Native/scout/precision/iterations | nominal 95 | 상대 DPS 개선% | 상태(PASS/BLOCKED/PARTIAL) | 원본 Native 증거 링크. 완료 전 행은 `NOT_RUN`.

**현재 상태:** 프로토콜 문서만 작성됨. IDEA-001/002/003/004/005/006/007 비교 실행 **0회**, 16개 신규 전문화 실측은 사용자 요청 v314 단계에서 별도 실행 대기 중. v290 기본값과 v313/v314 Actions 일정 변경 없음.

## 개발·합성 비교의 단계적 검증 규약 (2026-11-11)

- **첫째, 개선 아이디어 심사:** `README.md`의 이유·장점·단점·중복·통합/기각 기준을 통과한 후보만 실험 비용을 배정한다. 같은 v303/v312 기능을 복제한 독립 엔진을 동시에 개발하지 않는다.
- **둘째, 단독 부품 제거 시험(ablation):** 동일 신규 프로필과 동일 탐색 정책에서 **반경만**(IDEA-002), **전역 reserve만**(IDEA-003), **승급 일정만**(IDEA-001), **획득함수만**(IDEA-004) 바꾼다. 각 부분 변경 효과가 없다면 섞지 않는다.
- **셋째, 결합 이득 시험:** 유효했던 변경만 합쳐 `A+B` 와 `A`, `B` 및 기존 v290을 **동일 시간/iterations/Native source**에서 비교한다. 결합 정책의 기록에는 중복 Native 호출·cache 키·planner CPU/메모리·case 생성 I/O·동적 예산 충돌을 남긴다.
- **넷째, 일반화 검증:** 8개 DPS 전문화 × 2개 총량/상한·초기 순서를 바꾼 홀드아웃 시나리오에 대해 전문화 내 DPS 개선율과 각 5/10분 실측 확인 후보를 평가한다. 기존에 실험한 시나리오에서 규칙을 튜닝한 뒤 같은 결과를 독립 검증으로 다시 계산하지 않는다.
- **성과 미달의 처리:** 개선폭이 명목 95% 내라면 우위 미확정으로 유지한다. 테스트를 실패하거나 실측 원본이 부족한 조건은 집계에서 숨기지 않는다. '아이디어를 많이 등록했다'는 자체 성공 지표로 사용하지 않는다.

## v315 iterations vs wall-clock: 두 정식 평가축과 계측 요구조건 (2026-11-11)

**실측 근거:** [v315 원본 신규 프로필 10건 #42859573357](https://github.com/degong2-code/simc-secondary-optimizer-runner/actions/runs/42859573357) `SUCCESS`. v313 전부 8 + v314 사격사냥꾼 완료 2; 두 알고리즘 각각 1,008 호출. v312/v290 **iterations 비율 중앙값 0.568737**, **실제 wall 비율 중앙값 0.987107**, v312가 실제로 빨랐던 조건 **7/10**. 확인 후보 간 명목95 격차 확정 0/10. 상세 [개발 기록](../notes/2026-11-11_p2-v315-original-iteration-wall-evidence.md). 추가 Native 0.

**정식 제품 성능:** 새 사용자 프로필 같은 시나리오에서 시작시점부터 **5분/10분(300/600초)** 각각까지 원본 SimC가 완전히 완료된 320+ 정밀 확인 후보 중 최고 DPS·SEM·관측 1순위를 기록한다. 실제 CPU/월 타임 측정을 우선하고 엔진 계획·파일 처리·동시 호출·전투시간·SimC thread 등 환경을 봉인한다. 해당 시점에 320+ 후보가 없으면 `NO_CONFIRMED_CANDIDATE_AT_CHECKPOINT`로 보고, 이후 결과를 과거 시점으로 소급하지 않는다.

**정식 계산 효율:** 동일한 **총 SimC iterations**를 소모한 상태에서 위와 같은 확인 DPS·SEM/95를 비교한다. 후보 개수·반복 분포·Native 호출·planner/I/O 시간을 별도로 표시하고, 동일 iterations라도 종료시간이 다를 수 있음을 명시한다.

**현 증거의 한계:** v313/v314는 1,008 Native 호출만 맞췄을 뿐 *정식 동일 iterations* 또는 *동일 300/600초 체크포인트* 실험을 수행하지 않았다. 전체 wall 총계와 반복 수 두 점에서 스타트업 호출비용 및 한 iteration 처리시간 계수를 따로 추정하는 것은 **식별 불가능**하다. 비교자가 서로 다른 알고리즘·재측정 비율인 경우 오버헤드와 겹친다.

**추가 계측 설계 (본 커밋 구현 아님):** Native 요청마다 `(start_monotonic, finish_monotonic, exact_iterations, phase, cache_source, case_key_sha)`를 별도 append-only 로그로 남기고, planner 후보 계산·SimC subprocess·JSON2 검증·캐시/체크포인트 I/O를 분리한다. 취소·재개 후 전역 시간 정체성/누적 계산량이 왜곡되지 않도록 기존 sealed cache와 진행 counter에 결합한다. 추가 로그의 CPU/파일 비용 자체도 측정한다. 본 지표가 충족된 이후에만 IDEA-001의 적응형 35/120/320 승급 또는 시간 예산 예측을 실전으로 시험한다.

**결론:** 계산량은 'iterations로 공정하게 비교', 제품은 '동일 실제 시간으로 비교'의 **두 축을 각각 검증**한다. 수치가 동등하지 않은 결과는 승격 근거로 사용하지 않는다. 사용자 작업 v313→v314 기존 순서와 v290 기본은 변함없음.

## v316 옵트인 계측의 실제 활용 조건 (2026-11-11)

- **계측 구현:** [v316 time trace](../../../runner/v316_optin_case_time_trace.py)와 [원본 v291](../../../runner/v291_durable_multiscale_native_runner.py)의 `case_timing_trace=True`. V291_SESSION/저널·원본 SimC SHA를 변경하지 않으며, 기록을 활성화하지 않은 기존 실험에서는 과거 시점을 조작해 보완하지 않는다.
- **공정 300/600초 판정:** 단일 프로세스 실행에서 기록이 모든 저널 case를 덮고, 본래 원본 SimC에서 완료된 정밀 후보만 기준으로 시점별 관측 최고 DPS·SEM를 사용. 기록 누락·취소/재개·cache replay나 여러 invocation이 섞이면 `UNAVAILABLE`로 거절한다. 실제 사용자 클릭→시즌 환경/프로필 생성은 별도 시간이다.
- **시뮬레이션 비용 측정:** planner/pending, request/preflight, v065 engine.execute_one (subprocess 및 source/cache 포함), original JSON2 ingest, journal/checkpoint 구간을 독립 기록. 이 계측도 append/fsync 비용을 추가하므로 Native-only 처리시간으로 과장하지 않는다.
- **단계적 아이디어 검증:** IDEA-001은 기존 v290 확인 정책을 대체하지 않고 정확한 시간·iterations 예산을 관측한 후에만 다음 35→120→320 승급 옵션 실험 가능. 현재 original runner는 `scout_iterations`/ `confirm_iterations` 두 exact case ID만 허용하므로 새로운 120 단계의 캐시 키/취소/재개 확장 시험이 사전 필수다.
- **증거 범위:** 신규 실 Native 계측 실행 **미실시**. 오프라인 synthetic 계약 시험만 통과하는 것은 더 빠른 최적화 성능이나 95% 우위가 아니다. 기존 v313·v314의 1008 Native 동등 실험은 여전히 **서로 다른 iterations 예산**이다.

## 2026-11-11 직접 정책 교정 — 최종 품질/효율, 10분 유연한 목표
- **5/10분은 필수 관측 체크포인트이지 HARD STOP/탈락선이 아니다.** 600초 이후의 품질 개선은 폐기하지 않는다. 장시간 연구가 유효하면 900/1800초 또는 적응형 종료 시점의 확인 DPS/SEM을 추가 기록한다. 실제 사용자의 일반 목표 5~10분과 여러 시간의 연구 허용을 혼동하지 않는다.
- **평가 순서:** (1) 정확한 입력/Native/캐시 봉인·중단 재개, (2) 동일 총 SimC iterations 비교, (3) 동일 실제 300/600초 및 추가 시점 비교, (4) 확인 DPS/SEM와 CPU·메모리·I/O까지 표시한 시간-품질 Pareto 분석, (5) 여러 전문화·총량/상한의 실패·부분 완료 포함 재현성. 단일 척도로 허위 승자 판정하지 않고 선택된 후보 95%의 다중비교 한계를 명시한다.
- **IDEA-001 통합 가설:** 별도 IDEA ID 또는 실행기 없이 v316 per-case 측정으로 정밀 확인 기회를 보호하는 선택형 예약만 먼저 검증. 새 120 iteration 단계는 기존 v291 35/320 identity/seal/replay 계약 변경을 수반하므로 선행 검증 전 구현 금지.
