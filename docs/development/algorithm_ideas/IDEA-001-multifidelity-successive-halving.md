# IDEA-001 — 다중 정밀도 경쟁 탐색 (Multi-Fidelity Successive Halving)

- **제안:** 현재 대화, 2026-11-11. **상태:** `IDEA_ONLY`; 구현·Native 검증 **없음**. v290/v312의 기존 iteration 일정과 혼동 금지.
- **가설:** 같은 5–10분 예산에서 모든 후보에 고정 SimC iterations를 쓰는 대신, 다수 후보를 저정밀 측정하고 일부를 재측정하면 더 높은 확인 DPS에 빨리 도달할 수 있다.
- **후보 절차:** 신규 사용자 프로필의 허용 CHMV 공간에서 초기 후보 분산 → 35 iterations 1차 → 약 120 iterations 승급 → 최종 320 이상 iterations 정밀 확인. 35/120/320은 **제안값이며 승인된 SimC 소모량/시간 측정 아님**.
- **승급 기준:** DPS·SEM으로 성능 불확실성을 고려하고, 가까운 후보들만 과도하게 남기지 않도록 다른 지역의 대표 후보를 보호한다. 단일 scout 최고값으로 탈락 확정 금지.
- **초기화:** 과거 프로필·최고 스탯·DPS Native 결과로 시작하지 않음. 같은 신규 source와 실험별 초기 좌표 설계를 고정한다.
- **구현 재사용:** v291 Native JSON2·SEM·95·cache/resume 및 v290의 CHMV 정규화·제약 확인. SimC의 proc·APL·효과·DPS는 재구현하지 않는다.
- **평가:** 동일 신규 프로필에서 v290·v312·다른 아이디어와 동일 wall 5/10분, 실제 총 SimC iterations 및 정밀 측정 횟수 기록; 모든 전문화 내 상대 최고 확인 DPS, 시간별 개선 곡선, 선택쌍 명목95(다중 선택 교정 없음)를 함께 비교한다.
- **위험:** 35-iteration 과대평가와 이른 제거; 지역 고점 소실; SEM이 작은 구간에 불필요하게 예산 소모. 승급률은 사전 고정 후 실제 데이터로 비교한다.
- **승격:** 대안 대비 범용 성능이 여러 전문화/서로 다른 T·상한에서 반복 검증되기 전까지 **제품 기본값 변경 금지**.

## 사전 타당성 심사 — 2026-11-11

- **떠올린 이유/실측 문제:** v312 1008회는 정밀 재측정 16회·총 39,840 iterations, v290 1008회는 정밀 재측정 121회·약 69,765 iterations였다. 호출 수를 통제해도 반복 측정 예산과 결과의 신뢰도는 다르다. 35-iteration 1차 관측은 상당한 SEM을 가지므로 승급 결정을 명시적으로 관리할 근거가 있다.
- **기존 기능과 중복:** **중간~높음**. v290 `_precision_action`에서 이미 불확실한 우수 후보 재측정을 선택한다. 따라서 '다시 측정하기' 자체는 새 알고리즘이 아니다. 제안의 검증 가능한 차이는 **고정된 다단계 35→120→320 승급 비율과 신뢰도·지역 대표성 기반 탈락 규칙**뿐이다.
- **장점:** 낮은 반복 수로 여러 지역을 먼저 관찰한 다음 값비싼 320+ 반복을 필요한 후보에 집중할 수 있다. SimC 프로필·효과 모델 변경이나 새 대리모델 학습이 필요하지 않고, 기존 v291 exact case/iterations identity·재개에 통합 가능하다.
- **단점/실패 조건:** 최초 35-iteration 추정치의 높은 노이즈가 진짜 고점의 조기 탈락을 일으킬 수 있다. 120회 승급이 최종 재측정 전 중복 호출·I/O를 늘릴 수 있고, 빠르게 찾던 v290의 기회비용이 증가할 수 있다. '후보별 독립 SimC 실행'으로 인한 추가 비용도 통제해야 한다.
- **효율적으로 작동할 합당한 이유:** 분산이 큰 35-iteration 결과를 최종 결론으로 쓰지 않으면서, 모든 후보에게 높은 정밀도를 적용하지 않는 **계산량 배분 문제**에 직접 대응한다. 단, 순위 판정이 충분히 정확해지려면 반복수 증가가 SEM을 줄인다는 실제 조건을 확인해야 한다.
- **통합 우선안:** **v290 기존 정밀 후보 선택기에 선택형 승급 일정만 추가**. 완전히 새로운 탐색 엔진으로 독립 구축하지 않는다. IDEA-002의 복수 영역 대표 후보 보호를 승급 필터에 붙이면 고점 조기 제거 위험을 줄일 수 있다.
- **기각/보류 기준:** 동일 총 iterations·wall-clock에서 v290보다 5/10분 최고 재확인 DPS가 나아지지 않고 조기 탈락/중복 SimC가 늘면 보류. 개별 35/120/320 선택 결과는 원본 SimC 기록으로 확인하며, 명목95와 다중 선택 편향을 분리.
- **심사 결론:** `INTEGRATE_FIRST` / 독립 신규 엔진 우선순위 낮음. **현재 구현·효능 미검증.**

## 실측 예산 연구 업데이트 — v315, 2026-11-11

- **사실 근거:** [v315 신규 프로필 실제 10건 원본 영수증 #42859573357](https://github.com/degong2-code/simc-secondary-optimizer-runner/actions/runs/42859573357)에서 v312/v290 총 iterations 중앙값 비율 **0.568737**, wall-clock 중앙값 비율 **0.987107**, v312의 iterations 10/10건 적지만 실제 빠른 조건은 **7/10건**. 실제 Native 추가0, 독립 35→120→320 아이디어 실험 **0회**.
- **왜 필요한가:** iterations를 43% 줄였다는 숫자를 사용자 실행시간 43% 절약으로 잘못 이해하면 구현 방향이 틀어진다. 사용자 경험은 실제 5/10분 확인 DPS로 판단하고, 동일 iterations 조건은 계산 예산의 공정성을 검증하는 보조 축이어야 한다.
- **효율 작동 조건:** 다른 후보를 새로 SimC 실행할 때 **요청당 시간과 iterations의 실측 관계**가 비교적 안정적이고, 낮은 정밀도 후보만으로도 320+ 확인 후보를 적절히 선별할 수 있어야 한다. 현재 하나의 정책별 aggregate (I,t)에는 초기화·JSON/검증/계획 시간과 반복수 차이가 섞여 있어 두 비용계수를 식별할 수 없다.
- **장점:** 추가 SimC 없이 같은 신규 source의 완료된 요청 자료로 워크로드 차이를 사후 확인할 수 있다. 장기적으로 계측 후 남은 wall 시간에서 **확인 재측정 reserve**를 보장하는 정책과 통합할 수 있다.
- **단점/중복·통합:** 원래 v290 `_precision_action`과 IDEA-001 승급은 중복성이 있다. 35/120/320을 한 번에 적용하면 현재 v291의 **정확한 scout/confirm 두 iteration identity** 및 cache/replay seal이 깨지므로 독립 엔진을 도입하기보다 기존 정밀도 계획자에 선택형 승급을 신중하게 설계해야 한다. 처리속도 추정이 틀리면 남은 10분 내 정밀 확인이 실패할 수 있다.
- **연구 결론:** `IDEA_ONLY / OFFLINE_COST_AUDIT_VERIFIED`. iteration-vs-wall 측정 방법만 오프라인 구현·실증됐으며 **IDEA-001의 최적화 개선 여부는 미측정**. [연구 상세](../notes/2026-11-11_p2-v315-original-iteration-wall-evidence.md).
- **반증 조건:** 충분한 요청별 duration/phase 로그가 확보된 뒤 동일 iterations 및 동일 5/10분에서 v290 대비 320+ 확인 DPS·SEM·유효 확인 후보 수·총 CPU/IO 비용이 개선되지 않으면 단계적 승급은 채택하지 않는다.

## v316 실행시간 계측 선행조건 구현 — 2026-11-11

- [v316 측정 모듈](../../../runner/v316_optin_case_time_trace.py)과 [실행기 연결](../../../runner/v291_durable_multiscale_native_runner.py)에 **기존 Native/후보 정책 변경 없는 실측 옵션 `case_timing_trace=True`**를 구현했다. 상세 [개발 노트](../notes/2026-11-11_p2-v316-optin-per-case-wall-trace-and-confirmed-checkpoints.md).
- **원인·작동 이유:** v315 10개 실측에서 v312 반복량이 43.1% 적어도 wall은 중앙값 약 1.3%만 짧았으므로, 후보별 실제 wall-clock과 320+ 정밀 확인 완료 시점을 모르면 5/10분 효율 비교가 불가능하다. 기존 v298의 scout-only 최근 11개 타이밍 기록은 5/10분 전체 확인 경로와 다르다.
- **추가 기능:** 원본 SHA·phase·iterations에 결속된 opt-in sidecar, planner/preflight/engine/ingest/checkpoint 5구간 시간; 단일 프로세스의 중단 없는 타이밍만 300/600초까지 완료된 정밀 결과로 집계. 재개/누락 시간/캐시를 측정 결과로 보정하지 않고 명시적으로 판정 불가 처리한다.
- **장점:** 새 SimC 없이 오프라인에서 정합성 검증 가능, v290/v312 본래 탐색기·캐시·저널·세션 SHA 원형 유지. **단점:** 타이머로 인한 append/fsync I/O 추가, 순수 SimC 내부 계산시간과 engine 호출시간은 같지 않음, 측정 예산 시작 전 환경·프로필 준비시간 별도.
- **기존 기능/아이디어 중복:** v298 throughput hint와 측정 범위가 일부 겹치지만 현재의 *모든 phase·완료 시각·확인 DPS 시점*은 기존 v298에 없는 정보다. IDEA-001의 최적화 정책 자체를 구현한 것은 아니므로 기존 v290 precision scheduler와 중복된 엔진을 추가하지 않는다.
- **실증 범위:** 오프라인 **합성 executor/fake Native만** 검증. 현실 v313/v314에 회귀적으로 실제 시각을 삽입하거나 단일 10분 시점 최고점으로 과장하지 않는다. 이 계측을 활성화한 신규 실 Native 비교가 완료돼야 시간예산 기반 정밀 승급이 유효한지 판단 가능.
- **다음 승인 검증:** 같은 신규 프로필에서 original v290/v312 동등 iterations 및 원본 확인 DPS·SEM 실측, Opt-in trace가 있으면 300/600초의 precision 후보 수·최고값을 비교. 35→120→320 3단계는 기존 두 exact iteration ID/캐시·재개 계약의 안전한 확장이 완료되기 전까지 기능 승격 금지.

## 2026-11-11 사용자 직접 결정 — 품질·총비용 우선, 10분은 목표이지 탈락선 아님

- **승인 변경:** 일반 사용자 5~10분은 유용한 반응성 목표일 뿐 하드 종료/알고리즘 폐기 문턱이 아니다. 10분 초과라도 더 높은 **실제 320+ SimC 확인 DPS/SEM**을 합당한 추가 iterations·wall·CPU·메모리·I/O 비용으로 얻는 정책은 연구·채택 후보로 유지한다. 실험에는 여러 시간을 허용하지만 최종 제품 기본 실행 목표는 투명하게 표기한다. 기존 300/600초 로그 체크포인트는 그대로 보존하며 900/1800초는 필요시 **추가 관찰점**으로만 기록한다.
- **이번 채팅의 한 가지 아이디어 구체화: IDEA-001의 `quality–cost Pareto / anytime confirmation reserve`.** 이전 IDEA-001 time-reserved precision의 고도화이지 별도의 IDEA-008이나 새 실행 엔진이 아니다. v290의 관측·후보 순위와 320 정밀 확인을 유지한 채, v316이 기록한 실제 새 Native 요청별 duration·phase·iterations를 이용해 다음 정밀 확인 한 쌍의 예상 추가 비용 범위를 **보수적**으로 계산하고, 탐색 후보와 확인 후보 사이 예산을 조절하는 선택형 정책이다. 10분 이후에도 개선 가능성이 확인되면 계속 탐색할 수 있게 한다. 추정 시간으로 SimC DPS를 대체하지 않는다.
- **관측 근거:** v313 8/8(v290 관측6/v312 2), v314 15/16 완전(v290 11/v312 4), 선택쌍 명목95 확정 0; 1,008 Native씩 같은 호출 수여도 v290 약69.5~70k iterations와 v312 39,840가 다르다. 과거 소스 원본 23완료조건 Job wall 메타의 기술통계에선 v312가 18/23에서 빠르지만 확인 고점은 6/23에서만 관측 우세. 동일 iterations·동일 wall로 수행한 공정 비교는 아직 아니다.
- **비용/품질 평가 구체화:** 프로필마다 `(최고 320+ 확인 DPS, SEM, 전체 iterations, 실제 elapsed, 확인후보 수, 원본 재개 성공, CPU/메모리/I/O)` 벡터를 기록하고 **Pareto 비지배** 관계로 분석한다. DPS가 낮고 비용도 높은 정책은 열위 후보, 비용은 늘지만 DPS도 개선되면 사용자 선택 가능한 품질/시간 절충으로 남긴다. 95% 미확정을 통계적 우위로 바꾸지 않고, 여러 후보 탐색에서 선택한 최고점은 전역 최적해가 아니다.
- **실험 단계:** (1) 먼저 v316 `case_timing_trace=True` 실 Native 1개 새 프로필에서 *측정 기능*만 확인하고 본 정책을 작동시키지 않는다. (2) 기존 35/320 신분·v291 seal/cache/취소/재개 불변인 **320 확인 예약 규칙만** offline ablation. (3) 동일 신규 소스·실행 조건을 가진 v290 대비 **동일 iterations A/B**와 **동일 실제 wall 300/600초 + 가능한 추가 장시간 checkpoints**를 분리 검증. 조건별 정밀 후보의 DPS·SEM·95(명목/다중비교 한계)를 비교한다. (4) 실제 이득이 확인된 이후에만 추가 120 반복 단계의 identity 확장을 별도 검증.
- **장점과 필요조건:** 누락된 정밀 확인 기회와 지나친 scout 확장을 줄일 가능성. 이득은 관측된 per-case 비용 분포가 충분히 안정적이며, 확인 후보를 지나치게 일찍 선택해 먼 고점을 놓치지 않을 때만 발생한다. 지역 대표성·전역 reserve는 v290/v303의 기존 기능 재사용.
- **단점·반증:** planner가 320 예약에 과도하게 보수적이면 높은 DPS 새 영역을 놓치고, 프로필별 요청시간 분산이 크면 예정 시간이 크게 빗나가며, fsync 계측 자체가 I/O/시간 비용을 추가한다. 동일 총 iterations에서 확인 DPS가 개선되지 않고, 추가 wall/CPU/메모리/I/O 비용 대비 Pareto 개선이나 선택지 보존 없이 열위가 되면 정책 HOLD. v316 계측 누락·캐시·복수 invocation 자료에서 과거 300/600초 경과점을 만들어내면 즉시 차단.
- **중복/통합 판정:** v290 `_precision_action`·IDEA-001 승급·v298 실행시간 hint·v312 global reserve와 중복하므로 **기존 IDEA-001 상세 파일에만 고도화 등록**, 신규 알고리즘 ID 0개. `v291` 단일 Native 예산 예약기를 유지. 이번 기록만으로 실제 알고리즘 개선 PASS·Native PASS를 주장하지 않는다.
