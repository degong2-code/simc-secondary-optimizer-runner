# P2 v315 — 실제 iterations 예산과 wall-clock 비용의 분리 검증 (2026-11-11)

- **Capability:** `OPTIMIZER.POLICY`, `DEV.CONTINUITY`.
- **Keywords:** v315, IDEA-001, iterations, Native calls, wall-clock, source-bound ten real scenarios, fixed overhead non-identifiable, cost accounting, 5/10min, adaptive precision, 95.
- **Prior evidence:** [v313 8/8 원본 Native 성공 #42843524976](https://github.com/degong2-code/simc-secondary-optimizer-runner/actions/runs/42843524976), [v314 신규 8전문화 16조건 진행 #42846073820](https://github.com/degong2-code/simc-secondary-optimizer-runner/actions/runs/42846073820) 중 최초 사격 사냥꾼 두 조건만 추가 집계. 두 정책은 각 case당 Native 정확히 1,008회지만 스카우트/정밀 비율 및 SimC 반복 수가 다르다.
- **Decision:** `REUSE`: iterations는 **동일 계산 예산의 주요 대사 지표**, 실제 wall-clock은 **사용자 5/10분 목표의 최종 지표**로 함께 사용한다. 한 쪽의 개선만으로 다른 쪽 개선을 주장하지 않는다. 새 독립 최적화 엔진 개발보다 IDEA-001 승급 일정의 비용모델 검증을 우선한다.
- **Changes:** [원본 compact 영수증 오프라인 집계기](../../../integration_probes/p2_v315_iteration_wall_real_receipt_analysis_offline.py), [부정확한 비용 분해 방지 합성 계약시험](../../../tests/test_p2_v315_iterations_wall_audit_offline.py), [독립 원본 Actions 워크플로](../../../.github/workflows/p2_v315_iteration_wall_real_receipts_offline_once.yml)를 추가. 기존 8개 v313 + 신규 2개 v314 영수증의 exact-case·동일 새 source SHA·각 arm 1,008 원본 Native cache-only 대사·best 320 DPS/SEM·원본 SHA를 검증한다.
- **Verification:** [v315 실제 원본 영수증 오프라인 연구 #42859573357](https://github.com/degong2-code/simc-secondary-optimizer-runner/actions/runs/42859573357) `SUCCESS`, 관련 자체 시험 **4 PASS**, **10 complete cases**(v313=8, v314=2), 신규 Native **0**. 모든 10개에서 v312의 iterations가 더 적음; v312 wall-time이 더 짧은 case는 **7/10**, 나머지 3/10은 더 길거나 동일. **v312/v290 iterations 비율 중앙값=0.568737**, **v312/v290 wall 시간 비율 중앙값=0.987107**. 10개 조건에 한정된 **명목 선택 두 후보 간 95 우위 판정 0**. 중앙값의 비율이며 두 알고리즘 총합 시간의 비율이 아님.
- **중요 해석 제한:** 두 정책의 Native 횟수는 동일하나 (t,I) 총계는 각 정책당 한 점이고, 서로 다른 후보 생성기·실행 순서·정밀 측정 비율을 가진다. 따라서 `t = α·calls + β·iterations`의 **α(호출·초기화 비용)** 및 **β(iteration당 계산시간)**은 이 10쌍으로 식별할 수 없다. per-request 추적이 없으므로 5분/10분 **시점별** 최고 확인 DPS 도출도 불가능. iteration당 유효 wall-throughput은 오버헤드를 포함한 기술적 비율이지 SimC 고유 물리 처리속도가 아니다.
- **다음 실험 설계 (아직 미구현):** 단일 새 source/동일 시나리오에서 Native 요청별 `monotonic 시작·종료`, 실제 요청 iteration, 탐색/회귀 planner CPU, subprocess 런타임, JSON2 read/verify, checkpoint/write, 캐시 hit, 재시도·중단을 분리 기록한다. 기존 journal/case identity와 동일 SHA/취소·재개를 보존하고, 새 계측은 과거 Native 결과를 재실행하지 않게 한다. 원본 35/320 요청에서 서로 다른 반복수/케이스를 확보한 다음에만 보수적인 비용예측(최소 5/10분 종료 reserve)을 오프라인 검증한다. 실제 동등 iteration 시험은 v314 이후 별도 opt-in에서 새로운 사용자의 source를 독립 생성해 수행한다.
- **다음 의사결정:** 우선 측정 신뢰도와 차이를 대사. IDEA-001의 35→120→320 승급안은 현 v291에서 **scout/confirm 2개 exact iteration identity만 허용**해 새로운 120 단계가 session/case/cache 정체성을 바꾼다는 점을 해결하기 전 Native로 넣지 않는다. 비용이 실제 절감되고 5/10분 320+ 확인 DPS/SEM이 개선되는지 전 전문화 최소 부분집합에서 ablation 후 도입.
- **Remaining:** v314 16개 완주 후 누락 데이터/실측 wall ratio 및 전문화 다양성 추가 분석; 실제 비용과 planner 분해 측정은 **미구현**. 동일 iterations·동일 wall 예산 실험도 미실행이다. v290 기본과 main, 기존 v313·v314 실행 순서 변경 없음.
- **Efficiency:** 이번 분석 Native 추가 0, SimC binary·대표 시즌 DB 재수집 0, 과거 source cache 영구 동결 규칙 변경 0. 향후 타이머 변경은 planner 메모리/I/O, cache invalidation 최소화, 원본 계약을 별도 CI로 회귀 확인한다.
